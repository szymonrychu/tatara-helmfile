- 2026-07-17 (#195/#197/#199/#200) **Removing a CRD field is a TWO-REPO, ORDERED cutover, and `helmfile diff` cannot see either failure.** Removing `spec.scm.cron.mrScan` from the Project CRs cost two failed applies and left the platform paused with both `project-*` releases in `failed` status. Helm 4 builds a TYPED patch object against the live CRD schema; it does NOT rely on apiserver pruning, so it rejects a values/CRD mismatch in BOTH directions. (1) Values removed while the CRD still declares the field: SSA sends `mrScan: null` to delete a field its field manager owns, and the schema says non-nullable object -> `Invalid value: "null": must be of type object`. (2) Values still present after the CRD dropped the field: `failed to create typed patch object: .spec.scm.cron.mrScan: field not declared in schema`. So the values and the CRD MUST move together, operator first: ship the CRD removal, roll it out, THEN drop the values. The reverse order (what we did, on the theory that the operator's pin auto-propagates and would auto-apply the new CRD first) breaks the apply for every release in the bucket, and `--rollback-on-failure` cannot save it because the rollback hits the same typed-patch error. NOTE the asymmetry that misled us: `project-infrastructure` happened to land while `project-tatara` failed, so the first failure looked like a half-applied rollout rather than a schema fight. **`helmfile diff` passed green on BOTH broken states.** Diff does not construct the typed patch, so diff-green does not imply apply-green for a CRD field removal - the #51 diff gate does not cover this class. Recovery: revert the values, apply goes green, roll the operator, then re-land the values removal (#200).
